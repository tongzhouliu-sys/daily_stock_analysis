# 问股响应耗时分析与加速方案

状态：待评审 · 2026-11-11 · 基线 `89683b78`

问股里问一个问题要等很久，主要原因在流程结构。系统提示词要求模型分四个阶段依次取数，一次提问至少要完整请求大模型 4 次、串行跑 3 批工具，并且整段回答写完后才一次性显示。这不是某一处故障，可以加速。按本文方案，预计总耗时减少三到四成，开始出字的等待从整轮结束缩短到 20 秒以内。

本文的耗时数字是按代码结构和常见模型速度推算的量级。本地工作区没有线上配置、数据库和日志，线上实测值要靠第 0 步取得。拆分后的开发任务见 [问股加速开发任务书](stock-chat-latency-optimization-tasks.md)，其中第 1 批的工期细化后上调为 3–4 天。

## 一次提问现在怎么跑

以默认的单 Agent 模式（`AGENT_ARCH=single`）为例，问「分析一下 600519」：

```text
POST /api/v1/agent/chat/stream
├ 准备：确认标的、拼提示词、保存用户消息
├ 第 1 轮 LLM → 决定取 实时行情 + 日K线
├ 工具批次 1：实时行情、日K线（同批并行）
├ 第 2 轮 LLM → 决定取 技术指标 + 筹码分布
├ 工具批次 2：技术指标、筹码分布（同批并行）
├ 第 3 轮 LLM → 决定搜新闻
├ 工具批次 3：新闻搜索
├ 第 4 轮 LLM → 写完整回答（最长的一轮）
└ done 事件带回整段回答，页面这时才出现正文
```

等待期间页面只显示「分析过程」的步骤进度。

## 慢在哪里

按影响从大到小排列，代码事实均已对照基线核对。

1. **提示词强制四阶段串行。** 问股提示词规定行情与K线、技术与筹码、新闻、综合分析四个阶段必须依次执行，并明确禁止把不同阶段的工具放进同一次调用。执行循环本身支持一轮内并行跑多个工具，最多 5 个线程，是提示词把它限制成了串行。结果是 LLM 至少往返 4 次，其中 3 次只是为了决定下一步调哪个工具。[提示词](../../src/agent/executor.py#L431-L449) · [并行执行](../../src/agent/runner.py#L926)
2. **简单问题和追问没有短路径。** 提示词对「用户询问某支股票」一律要求走完四个阶段。问「现在多少钱」，或对刚分析过的股票追问止损位，模型照字面执行时也会整套重跑。
3. **回答不流式。** LLM 调用是一次性请求，等模型写完才返回。SSE 只在结束时用 `done` 事件带回全文，前端也只在这时写入正文。最后一轮写长回答通常是全程最长的一段，这段时间用户看不到任何正文。[适配层](../../src/agent/llm_adapter.py#L691) · [接口](../../api/v1/endpoints/agent.py#L650-L666) · [前端](../../apps/dsa-web/src/stores/agentChatStore.ts#L665-L680)
4. **数据源每次请求前无条件休眠。** efinance 和 akshare 的防封策略会在每次请求前随机休眠，efinance 1.5–3 秒，akshare 2–5 秒，距上次请求再久也照睡。这是为批量跑全市场设计的。问股时用户在等一只股票，这段时间是纯等待。日K线缓存未命中、筹码分布等走这两个源的调用都受影响，实际影响面取决于线上数据源优先级。[efinance](../../data_provider/efinance_fetcher.py#L331-L350) · [akshare](../../data_provider/akshare_fetcher.py#L453-L472)
5. **K线缓存在非交易时段恒不命中，同一轮内重复下载。** 读缓存的条件是库里最新一根K线的日期不早于自然日的今天。周末、节假日、开盘前，以及当日K线要到北京时间次日才有的美股，都不满足这个条件。于是 `get_daily_history`、`analyze_trend`、`calculate_ma`、`get_volume_analysis`、`analyze_pattern` 各自联网下载一次同样的K线，每次都叠加第 4 条的休眠。[缓存条件](../../src/services/history_loader.py#L165-L176)
6. **没有单次超时，慢源会拖到整体预算。** 工具分类超时默认都是 0，即不限制。单次 LLM 调用的超时等于整轮剩余预算，整轮默认 600 秒。SSE 等待下一个事件的上限是 300 秒。某个数据源或模型通道卡住时，用户会等几分钟才看到失败或降级。[工具超时默认值](../../src/config.py#L1134-L1137) · [LLM 调用](../../src/agent/runner.py#L465-L469) · [SSE 等待](../../api/v1/endpoints/agent.py#L727)
7. **所有轮次用同一个主模型，思考模式可能被强制开启。** 只输出工具调用的前几轮不需要强推理，却与写回答用同一个模型。主模型是 `deepseek-chat` 时，适配层会强制开启思考，每一轮都多一段思考时间。线上实际用哪个模型待确认。[强制思考](../../src/agent/llm_adapter.py#L101-L103)
8. **每轮携带的上下文偏大。** 每次请求都带全部 18 个工具声明。`get_daily_history` 默认把 60 根K线的完整字段原样返回，之后每一轮都要重新发送一遍。输入越长，每轮越慢、越贵。[K线返回](../../src/agent/tools/data_tools.py#L363-L384)
9. **多 Agent 模式下各阶段完全串行。** 如果线上配了 `AGENT_ARCH=multi`，技术、情报、风险、决策几个 Agent 依次各跑一个完整循环，LLM 轮数是单 Agent 的数倍。默认值是 `single`，线上配置待确认。[编排循环](../../src/agent/orchestrator.py#L649)

还有几处次要开销：每个请求都新建一次 LLM 适配器和 Router，每个进度事件都把完整步骤列表写一次数据库，以及实例休眠后的冷启动。它们合计通常在秒级以内，放在最后处理。[适配器构建](../../src/agent/factory.py#L653) · [进度落库](../../src/agent/chat_executor.py#L151-L170)

## 耗时量级估算

现状总耗时约等于 3 个短轮、1 个长轮和 3 个工具批次之和。

| 环节 | 估算 | 说明 |
| --- | --- | --- |
| 短轮 LLM ×3，只输出工具调用 | 每轮 3–8 秒 | 思考型模型每轮再加 10–30 秒 |
| 工具批次 ×3 | 每批 3–15 秒 | 含请求前休眠，数据源失败走降级时更长 |
| 长轮 LLM ×1，写回答 | 20–60 秒 | 取决于回答长度和模型输出速度 |
| 合计 | 约 40–130 秒 | 正文在最后一刻才出现 |

## 优化方案

### 第 0 步 · 取得实测分解

预计半天。后面每一步的取舍都以这一步的数据为准。

- 工具耗时已有记录。每条答复的「分析过程」里有各工具的耗时，同一份数据存在 `conversation_messages.thinking_steps_json`，其中 `agent_loop` 的 `stage_done` 带整轮耗时。服务日志里有 `Agent completed in N steps (Xs, T tokens)`。
- 缺的是每一轮 LLM 的耗时。在 runner 的 LLM 调用前后加计时并写一行日志，包含步号、模型、耗时、输入和输出 token 数。只加日志，不改事件契约。[LLM 调用位置](../../src/agent/runner.py#L465)
- 用 10 个真实问题取基线，首次分析与追问各半，覆盖 A 股和美股、交易时段和非交易时段。记录总耗时、LLM 轮数、每轮耗时和每个工具耗时。
- 确认线上配置：`AGENT_ARCH`、`LITELLM_MODEL`、`AGENT_LITELLM_MODEL`、各数据源优先级、`AGENT_*_TOOL_TIMEOUT_S`。

### 第 1 批 · 减少轮数和空等

预计 1–2 天。以提示词、配置和取数层的小改动为主，收益最大。

- **1-1 合并取数轮。** 修改问股提示词，要求第一轮一次性并行调用所需的行情、K线、技术指标、筹码和新闻工具。`CHAT_SYSTEM_PROMPT` 和 `LEGACY_DEFAULT_CHAT_SYSTEM_PROMPT` 两个模板同步修改。LLM 往返从 4 次降到 2 次，三个工具批次合成一个并行批次，工具耗时从三批之和变为最慢的那一个。这一项依赖 1-3，否则 `get_daily_history` 和 `analyze_trend` 并行时会各下载一次K线。
- **1-2 按问题取数。** 提示词改为按问题需要选工具。完整分析才取全套，只问价格、估值等单点信息时只调对应工具。追问优先使用本会话已取得的数据，数据超过 10 分钟或用户要求最新时再重取。追问可降到 1–2 轮。
- **1-3 修正K线缓存并在同轮内复用。** 缓存新鲜度改为对比最近一个应有K线的交易日，复用已有的 `get_effective_trading_date`。给 `load_history_df` 加按「标的 + 截止日」合并的并发去重和短时内存缓存，使同一轮里的多个工具共用一次下载。技术分析类工具联网取到的K线也写回数据库。[交易日历](../../src/core/trading_calendar.py#L239)
- **1-4 交互路径去掉无条件休眠。** 问股发起的取数只在距上次请求不足最小间隔时补足等待，取消每次请求前的固定随机休眠。每日分析、扫描等批量任务保持现状。每次联网取数省 1.5–5 秒。
- **1-5 配置单次超时。** 用现成配置项给工具设上限，建议起始值为 `AGENT_DATA_TOOL_TIMEOUT_S=20`、`AGENT_SEARCH_TOOL_TIMEOUT_S=20`、`AGENT_ANALYSIS_TOOL_TIMEOUT_S=30`，再按第 0 步实测的 P95 调整。另给单次 LLM 调用加独立上限，建议 90 秒，超时后进入现有的备用模型降级。这几个工具超时项对后台报告的 Agent 同样生效。
- **1-6 取数轮用快模型。** 用现成的 `AGENT_LITELLM_MODEL` 把问股 Agent 指向响应快的非思考型模型，并把 `deepseek-chat` 的强制思考改为可配置。先做配置对比，回答质量有疑虑时再考虑 3-3。

### 第 2 批 · 流式输出回答

预计 3–5 天。这一批不减少总耗时，但正文在最后一轮开始后一两秒内就出现，体感改善最大。

- **后端。** LLM 调用改为流式，新增 SSE 事件逐段下发正文，暂名 `content_delta`。`done` 仍带完整正文，保存逻辑不变。模型可能先输出几句话再发起工具调用，所以一轮内最终出现工具调用时，要下发一个撤回事件让前端清掉这段临时文本。流式中途失败后不能再静默切换备用模型，按本轮失败处理还是撤回后重试，在实现时确定。
- **进度落库要绕开。** 目前每个进度事件都会追加进步骤列表并整体写库。正文增量事件必须排除在收集和落库之外，否则会变成每个片段写一次数据库。[进度落库](../../src/agent/chat_executor.py#L151-L170)
- **前端。** 收到增量就追加渲染 Markdown，并做节流避免长回答卡顿。收到 `done` 后以服务端全文为准。刷新或断线恢复沿用现有的会话详情轮询。
- **契约与文档。** 新事件为追加式，同步更新事件契约文档。Bot 和非流式的 `POST /chat` 不受影响。[事件契约](../agent-stream-events.md)

### 第 3 批 · 结构性提速

按第 0 步和前两批之后的实测结果，决定做哪几项。

- **3-1 服务端预取。** 标的在调用模型之前已经由规则解析确定。对判定为完整分析的问题，服务端在第一轮 LLM 之前直接并行取标准数据包，作为上下文交给模型，LLM 只需 1 轮。这需要一个可靠的问题分类。误判成完整分析会多取数据，误判成简单问题则退回现有流程。
- **3-2 精简每轮上下文。** 问股场景下K线工具返回最近约 20 根加统计摘要。按标的类型收窄工具集，例如美股和港股不下发筹码工具。用已有的 `LLM_PROMPT_CACHE_DIAGNOSTICS_LEVEL` 确认提示词缓存是否生效。
- **3-3 两段模型。** 取数轮用快模型，最后写回答用强模型。需要改执行循环按轮选择模型，并处理不同模型之间思考内容不能互传的问题。
- **3-4 工程开销。** 跨请求复用 LLM 适配器与 Router，进度落库改为节流写入，服务启动时预热技能、工具注册表和数据源管理器。
- **3-5 多 Agent 并行。** 仅当线上使用 `multi` 时考虑。技术与情报两个阶段互不依赖，可以并行。

## 预期效果

以下均为估算，以第 0 步的实测基线为准重新核对。

| 指标 | 现状 | 第 1 批后 | 第 2 批后 |
| --- | --- | --- | --- |
| 完整分析总耗时 | 40–130 秒 | 25–80 秒 | 不变 |
| 完整分析开始出字 | 等于总耗时 | 等于总耗时 | 7–20 秒 |
| 简单追问总耗时 | 接近完整分析 | 10–25 秒 | 不变，5–12 秒开始出字 |
| LLM 往返次数 | 至少 4 次 | 完整分析 2 次，追问 1–2 次 | 不变 |
| 单个慢工具的最长等待 | 可达数分钟 | 20–30 秒封顶 | 不变 |

## 验证方式

- 每一批完成后，用第 0 步同一组 10 个问题复测，对比总耗时、开始出字时间、LLM 轮数和各工具耗时。
- 抽查回答质量。合并取数后，回答仍应引用行情、技术指标、筹码和新闻四类数据，结论与改动前同题回答没有实质退化。
- 在周末和开盘前各测一次同一只股票，确认同一轮内K线只联网下载一次。
- 后端执行 `./scripts/ci_gate.sh`。涉及前端的批次执行 `cd apps/dsa-web && npm ci && npm run lint && npm run build`，并验证桌面端加载同一份 Web 构建。
- 第 2 批需要补流式事件的后端与前端测试，覆盖先出文字后调工具的撤回、中途失败、停止接收和刷新恢复。

## 风险与回滚

- **数据源封禁。** 合并取数和去掉固定休眠后，短时间内的并发请求变多。对策是保留最小请求间隔、并发去重、缓存，以及现有的每批最多 5 个工具线程。批量任务的防封策略不动。
- **回答质量变化。** 提示词改动会影响取数范围和回答结构。问股提示词由 Web 问股和 Bot 聊天共用，两边都要抽查。每日报告使用另一套提示词，不在本次范围内。
- **流式兼容。** 新事件是追加的，`done` 语义不变。Web 和桌面端使用同一份构建，随后端一起发布。
- **新增配置。** 单次 LLM 超时、强制思考开关、流式开关都是新配置项，需要同步更新 `.env.example` 和相关文档，并保证不配置时行为与现在一致。
- **回滚。** 各项相互独立。提示词和配置类改动直接恢复原值。流式输出放在开关后面，关闭后回到一次性返回。缓存与休眠的改动按提交回退，不涉及数据迁移。

# 问股回复终态与可追问性修复需求

日期：2026-11-12。任务类型：fix。建议优先级：P0。状态：已实施。

核对基线：本地 HEAD `bd178b28` 及 2026-11-12 工作区。工作区存在其他未提交文档和脚本，本文只依据当前代码阅读与静态调用链核对，不代表线上运行版本。

本文需求已由[开发任务书](stock-chat-stream-terminal-recovery-tasks.md)落地；改动尚未提交，也未部署到线上。

## 1. 结论

用户反馈的“问完问题后卡死、决策 Agent 已完成但无法追问、停止按钮也关不掉”是真实缺陷，不是单纯的界面错觉。当前代码至少存在四类互相叠加的问题：

1. 多 Agent 问股执行器与流式接口的参数契约不一致，当前 HEAD 会在执行前直接报错。
2. 多 Agent 执行完成后没有清理服务端的“运行中”状态，刷新、切换会话或轮询会把界面重新拉回加载态。
3. 前端把 `done` 事件只当作“内容暂存”，真正结束要等 SSE 连接 EOF；连接不关闭时，回复永远不落地，停止按钮常驻。
4. 停止按钮只中断浏览器请求，没有让在途的轮询和会话详情请求失效；这些迟到响应可以把 `loading` 再改回 `true`。

上一轮修复（`fe86c36f`）解决了单 Agent 的导入错误和 `stopStream` 的本地状态清理，但没有覆盖多 Agent 的终态清理、流结束判定和轮询竞态，因此用户仍可能看到相同现象。

## 2. 用户现象与复现条件

### 2.1 典型现象

- 问股页面发送问题后，进度区显示“决策 Agent 已完成”或类似终态。
- 输入框仍不可用，发送按钮仍是停止按钮。
- 点击停止后按钮短暂恢复，随后又变回停止状态，或刷新后继续显示运行中。
- 无法发送追问；即使输入框恢复，重新发送也可能立即回到加载态。
- 页面刷新、从左侧切换回该会话、重新打开 Desktop 后仍显示运行中。

### 2.2 复现条件

- `AGENT_ARCH=multi`，即问股使用 `AgentOrchestrator`。
- 出现以下任一情况即可触发或放大问题：
  - 正常完成一轮多 Agent 分析后刷新/切换会话；
  - 执行过程中点击停止；
  - SSE `done` 已到达但连接没有立即关闭；
  - 停止时恰有一个轮询或会话详情请求在途。

### 2.3 当前 HEAD 的前置阻断

当前 HEAD 的多 Agent 流式路径还有一个更早的阻断缺陷：

- `api/v1/endpoints/agent.py:749-753` 无条件调用 `executor.execute_turn(..., stream_content=...)`。
- `src/agent/orchestrator.py:522-527` 的 `execute_turn` 没有 `stream_content` 参数。
- `build_agent_chat_executor` 在 `AGENT_ARCH=multi` 时返回 `AgentOrchestrator`（`src/agent/factory.py:642-644`）。

因此严格按当前代码运行，多 Agent 问股会在开始执行前抛 `TypeError`，由 `run_sync` 转成 `error` 事件。用户如果仍能看到“决策 Agent 已完成”，说明实际运行的是尚未包含这次调用的旧构建；这不能否定下面的终态问题，反而说明“决策完成但界面不结束”与多 Agent 的运行状态生命周期直接相关。

### 3.1 为什么上一轮修复没有解决

- `fe86c36f` 的 `await` 修复只影响单 Agent 的 `chat_executor.py`；多 Agent 走 `orchestrator.py`，不受该修复影响。
- `stopStream` 改为立即清 `loading` 只解决了“当前这一刻”的本地状态；服务端仍是 `is_running=true`，轮询/详情一旦返回就会把状态恢复。
- 前端仍以 EOF 作为流结束条件，因此 `done` 到达但连接保持时，修复不会生效。

## 4. 目标与非目标

### 4.1 目标

- 任意终态（成功、失败、超时、停止接收、断线）后，问股界面在 1 秒内恢复可输入、可发送。
- 任意终态后，服务端不再把该轮次报告为运行中；刷新、切换会话、重新打开 Desktop 结果一致。
- 多 Agent 与单 Agent 使用同一套终态语义、消息保存和运行状态清理规则。
- 停止按钮只负责“停止接收当前回复”时，也必须立即结束当前界面加载态，并且不被迟到响应复活。
- `done` 是客户端可依赖的终点，不要求等待 SSE 连接 EOF。
- 停止后用户可以直接追问；旧轮次的迟到结果不能覆盖新轮次，也不能清除新轮次的运行状态。

### 4.2 非目标

- 不优化模型速度、工具耗时或报告质量。
- 不重做问股页面视觉，不新增分析能力。
- 不把“停止”默认改造成强制终止模型调用；是否增加真正的服务端取消接口，作为独立产品决策，见 R8。
- 不改变报告、定时任务、Bot 命令和交易执行链路；Bot 复用同一执行器时只继承终态修复。
- 不处理与本问题无关的 Answer Editor 缺失方法、进度事件持久化告警等附带发现，另立任务。

## 5. 功能需求

### R1 · `done` 是终态，不依赖 EOF

- 客户端收到合法 `done` 后，必须立即用该事件的 `content` 构造/更新助手消息，结束加载态，恢复输入框和发送按钮。
- 即使连接在 `done` 后保持打开、网关缓冲、代理未关闭，也不得继续等待；客户端应主动取消 reader 并结束本轮。
- `done.success=false`、`error_code=timeout`、`error_code=cancelled` 同样是终态：显示对应失败/超时/已停止状态，不能让界面停留在运行中。
- `done` 之后到达的同一请求事件一律忽略，不能重复追加消息。
- 兼容旧服务端：没有 `done` 但连接正常关闭时，保留现有“回复未完整返回”的错误提示；不能静默当成功。

**验收：** 构造一个发送 `accepted` + `done` 后不关闭的 SSE 流，页面在 1 秒内显示完整回复、输入框可用；关闭连接后不产生第二条消息。

### R2 · 多 Agent 的终态清理与单 Agent 对齐

- `AgentOrchestrator.execute_turn` 必须在 `try/finally` 中执行，所有退出路径都要：
  - 保存成功或失败助手消息；
  - 将 `is_running` 置为 false；
  - 清空或归档本轮运行进度；
  - 释放本轮运行归属。
- 成功、返回失败、超时、异常、客户端断开、进程内取消均适用；不能只在正常返回时清理。
- 清理顺序必须是“助手终态消息已保存 → 运行状态清除 → 发送 `done`”，保证刷新时不会看到“已完成但仍在运行”或“已停止但消息丢失”。
- 多 Agent 的 `execute_turn` 接受 `stream_content` 参数；当前不实现正文增量时也必须安全忽略，不能因参数不匹配阻断整轮执行。

**验收：** 多 Agent 成功、失败、抛异常三种路径执行后，会话详情 `is_running=false`；异常路径仍有可读的失败消息；刷新不再恢复运行中。

### R3 · 运行状态按轮次归属，避免旧轮次清理新轮次

- 运行状态不能只是会话级布尔值，必须能标识当前运行轮次（如 `running_turn_id` 或 `running_request_id`）。
- 只有当前归属轮次可以更新进度、清除运行状态；旧轮次的迟到完成、异常或断线清理不得清除新轮次的运行状态。
- 新轮次被接受时，应明确接管运行归属；旧轮次即使仍在后台执行，也只能写自己的终态消息，不能改写会话的当前运行标记。
- 客户端轮询/详情读取以服务端返回的轮次归属为准；归属不匹配时不得把界面切回运行中。

**验收：** 旧轮次尚未结束时开始新轮次，旧轮次随后结束，不得把新轮次显示为已停止；新轮次的进度和终态保持正确。

### R4 · 停止按钮立即生效，且不被迟到响应复活

- 点击停止后，客户端必须立即：
  - 将本轮标记为已停止/已分离；
  - 清空 `loading`、`progressSteps`、当前请求归属；
  - abort 当前 SSE reader；
  - 使所有在途轮询、详情读取和旧请求回调失效。
- 停止后不得因为一次迟到的轮询响应、会话详情响应或旧 SSE 事件重新进入加载态。
- 停止按钮必须可重复点击且无副作用；停止后按钮立即切回发送按钮。
- 停止语义仍为“停止接收当前回复”，不承诺后台模型立即停止；界面文案和状态应避免让用户误以为服务端一定已取消。
- 如果后续实现真正的服务端取消，沿用本条的“立即结束界面加载态”要求，但不得把等待取消确认作为恢复输入的前提。

**验收：** 在轮询请求发出后、响应返回前点击停止；响应返回后 `loading` 仍为 false，消息列表不被旧响应改写，发送按钮可用。

### R5 · 轮询与详情读取必须有请求归属校验

- 轮询任务必须在发起时捕获：
  - 会话 ID；
  - 会话代次/epoch；
  - 轮询令牌（每次启动/停止递增）；
  - 发起时的 `loading` 状态。
- `await` 返回后必须重新校验以上全部条件；任一不匹配直接丢弃响应，不得 `set` 任何 UI 状态。
- `readDetail` 同样必须校验请求序号；停止操作应使已发出的详情读取失效。
- 切换会话、新建会话、刷新会话、停止接收都应递增对应令牌，不能只依赖 `sessionId` 判断。
- 轮询错误仍可静默重试，但不得在已停止后继续重试或重新拉起 loading。

**验收：** 停止、切换会话、新建会话三种操作分别与在途轮询/详情请求交叉执行，界面最终状态只由最后一次用户操作决定。

### R6 · 恢复运行中状态要有边界，不能永久卡住

- 会话详情应返回足够的运行信息：`is_running`、当前运行轮次标识、最近心跳/更新时间（字段名实施时统一）。
- 客户端只在“服务端明确运行中且心跳未过期”时恢复运行态；心跳超过阈值或服务端明确已结束时，显示“上一轮分析可能已中断”，恢复输入能力。
- 服务端在进程启动或定时清理时，应修复崩溃/重启遗留的 `is_running=true`。
- 现有 `hasUnfinishedTurn`（最后一条是用户消息）只能作为辅助证据，不能单独支撑无限期加载。
- 恢复阈值应集中配置，避免前端、后端各自散落魔法数字。

**验收：** 手工把数据库中的 `is_running` 置为 true 且心跳过期，刷新页面后显示可追问状态；不会无限轮询。

### R7 · 追问可用性与消息一致性

- 终态后输入框立即可用；发送追问不依赖用户刷新或等待后台旧任务结束。
- 新追问被接受后，旧轮次的迟到 `done`、错误、进度不得追加到新轮次的消息列表。
- 助手消息优先使用 `done.assistant_message_id` 作为稳定 ID；没有稳定 ID 时才使用临时 ID，并在详情返回后按 ID 归并，不能重复插入。
- `done.thinking_steps` 存在时优先使用服务端快照；缺失时才使用浏览器实时收集的步骤。
- 消息 ID 统一按字符串比较，兼容服务端数值 ID。

**验收：** 连续两轮问答、刷新、切走再切回，消息数量和顺序稳定；每轮过程步骤与详情一致。

### R8 · 多 Agent 流式契约与可选取消能力

- 多 Agent 执行器必须与单 Agent 的流式调用契约兼容；`stream_content` 参数、`done` 字段和错误码保持一致。
- 如果产品决定把“停止”升级为“取消本轮分析”，新增服务端取消接口时必须满足：
  - 按 `session_id` + `request_id`/`turn_id` 精确取消；
  - 幂等，重复调用不报错；
  - 取消后运行状态最终为 false，终态消息可读；
  - 多进程/多副本部署使用共享状态或数据库标记，不能只依赖单进程内存。
- 该取消能力是 P1 可选项，不阻塞本需求 P0 验收；不实现时，R3 的轮次归属和 R4 的本地停止必须成立。

## 6. 验收标准

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 多 Agent 正常完成 | `AGENT_ARCH=multi` 提问并等待完成 | 收到 `done` 后 1 秒内显示正文、输入框可用；详情 `is_running=false` |
| 多 Agent 失败 | 让执行器抛异常或返回失败 | 显示失败消息；1 秒内恢复输入；详情 `is_running=false` |
| 多 Agent 刷新 | 完成后刷新/切走再切回 | 不显示运行中；消息和过程步骤与完成时一致 |
| `done` 后连接不关闭 | 模拟 SSE 保持打开 | 仍立即结束加载并显示回复；关闭连接不产生重复消息 |
| 停止时有在途轮询 | 轮询请求 pending 时点击停止，再让请求返回 | `loading` 保持 false；旧响应不追加消息、不恢复停止按钮 |
| 停止后追问 | 停止后立即发送新问题 | 新问题可发送并正常完成；旧轮次迟到事件不影响新轮次 |
| 旧轮次与新轮次重叠 | 旧轮次未结束时开始新轮次 | 旧轮次结束不清除新轮次运行状态；消息不串轮 |
| 心跳过期恢复 | 手工制造 stale `is_running` | 刷新后显示可追问/中断提示，不无限轮询 |
| 会话切换 | 运行中切到另一会话再切回 | 只显示该会话真实状态；不发生跨会话消息写入 |

## 7. 兼容性与发布边界

- API 新增运行轮次/心跳字段应为可空追加字段，旧客户端忽略即可；不改变 `accepted`、`done`、`error` 的既有必填字段。
- SSE 继续保持 `done`/`error` 终止语义；不新增客户端必须认识的终止事件。若新增 `error_code=cancelled`，旧客户端按普通失败处理即可。
- 数据库迁移只追加可空列，不删除、不重建现有会话表；回滚旧版本仍能读取正文和历史消息。
- Web 与 Desktop 共用构建产物，修复 Web 后需验证 Desktop 加载同一构建；Bot 复用执行器时只继承服务端终态修复。
- 若生产是多 worker/多副本，运行状态和取消标记不能只放进程内存；本期至少保证单进程正确，多副本方案在实施前确认部署形态。

## 8. 风险与回滚

- **取消/停止与终态写入竞态。** 必须用轮次归属做条件更新，不能用无条件的 `set_running(false)`，否则旧轮次会清除新轮次状态。
- **提前结束流导致重复消息。** 使用 `assistant_message_id` 归并，并在详情/轮询侧做 ID 去重；流式追加和详情恢复共用同一消息映射。
- **旧客户端兼容。** 新增字段必须可空，`done` 语义保持；不能要求旧客户端先升级才能继续使用。
- **误判心跳过期。** 阈值要覆盖正常长任务；先只用于“无心跳的 stale 状态”，不替代正常运行中的进度事件。
- **回滚方式。** 代码回滚到修复前版本；数据库新增可空列保留不影响旧版本读取；已保存消息不迁移、不删除。回滚后仍需接受“多 Agent 运行状态可能残留”的已知风险。

## 9. 实施前待确认

1. 生产实际 `AGENT_ARCH` 是 `single` 还是 `multi`，以及线上运行的 commit；这决定 B1 是否已经暴露。
2. 生产部署是单进程还是多 worker/多副本；决定运行状态和取消标记的存储方式。
3. 产品是否要把“停止”从“停止接收”升级为“取消本轮分析”；本需求 P0 不依赖该能力。
4. stale running 的心跳阈值和清理周期；建议由后端统一配置并下发，不在前端硬编码。
